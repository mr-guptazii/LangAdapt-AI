# Database

PostgreSQL 16+, SQLAlchemy 2 (async ORM), Alembic migrations. UUID primary keys throughout; `created_at`/`updated_at` on every table via `TimestampMixin`.

## Migrations

Four migrations in `apps/api/alembic/versions/`, forming a diamond (one branch point, one merge point):

```
168d079a7f17 (initial schema, 30 tables)
     ├── a1b2c3d4e5f6 (semantic_memory — needs pgvector)
     └── b2c3d4e5f6a7 (analytics_and_usage — analytics_events + ai_usage_logs, no pgvector needed)
              └── c3d4e5f6a7b8 (merge — no-op, just unifies the two branches back to one head)
```

1. **`168d079a7f17_initial_schema`** — 30 tables, autogenerated from the SQLAlchemy models against a live Postgres instance, then hand-split (see #2).
2. **`a1b2c3d4e5f6_semantic_memory`** — isolated on purpose: `CREATE EXTENSION IF NOT EXISTS vector` + the `semantic_memories` table. This is the *only* migration with an extension dependency.
3. **`b2c3d4e5f6a7_analytics_and_usage`** — `analytics_events` + `ai_usage_logs`. Branches directly off #1 (not chained after #2) specifically so these two tables — which have nothing to do with pgvector — stay reachable even on a database where the extension isn't installed.
4. **`c3d4e5f6a7b8_merge_heads`** — a no-op merge (`down_revision = (a1b2c3d4e5f6, b2c3d4e5f6a7)`) so `alembic upgrade head` resolves to one target again once both branches are applied.

```bash
alembic upgrade head           # all four (requires pgvector)
alembic upgrade b2c3d4e5f6a7   # 32 tables minus semantic_memories — the reachable head without pgvector
alembic heads                  # shows the single merged head once both branches exist
alembic history                # shows the full branch/merge graph
alembic revision --autogenerate -m "description"   # after changing a model (requires DB at head — see note below)
```

Note: `alembic revision --autogenerate` refuses to run against a database that isn't at its current head (a safety check). On an environment without pgvector, the DB can only reach `b2c3d4e5f6a7`, not the true head — the `analytics_and_usage` and `merge_heads` migrations in this repo were therefore hand-written (not autogenerated) against that constraint; see their docstrings.

## pgvector note

`semantic_memories.embedding` is a `pgvector.sqlalchemy.Vector(384)` column, queried via cosine distance (`.cosine_distance()`) for top-K semantic memory retrieval.

- **Docker Compose**: uses the `pgvector/pgvector:pg16` image — the extension is preinstalled, both migrations succeed, everything works.
- **Native Postgres without the extension**: the `semantic_memory` migration fails cleanly with `extension "vector" is not available` and rolls back (the other three migrations are unaffected — verified during development: all 31 non-vector tables create and serve real traffic against a native Windows Postgres 17 install with no `vector` extension). `app/memory/service.py` wraps both the write and the read in a `SAVEPOINT` (`db.begin_nested()`) and catches `DBAPIError`, so a missing table degrades to "no memories retrieved" for that call rather than failing the whole conversation turn. Install the extension (https://github.com/pgvector/pgvector#installation) to get full semantic retrieval on a native install.

## Security / tenant isolation (section 36)

Every learner-data endpoint depends on `core/deps.get_learner_profile`, which resolves the caller's *own* `LearnerProfile` from their JWT — no endpoint accepts a client-supplied `learner_profile_id`. Foreign keys use `ondelete="CASCADE"` where a child row has no meaning without its parent (e.g. deleting a user cascades through `learner_profiles` → `skill_mastery`/`learner_errors`/etc.).
